# buddy 发布前检查：四类红线 + 一条命令

本 Skill 是 buddy 项目**发布前体检**的通用套路，只写「查哪几类、怎么判、FAIL 了怎么办、怎么留证」，
**不复制任何具体密钥值 / 接口条数 / 文件清单**——那些的唯一定义处见 §1。

## 0. 一句话

发布（推公网仓 / 上线服务器 / 对外演示）之前，跑 `scripts/release-check.sh` 一条命令；
它只读不改，逐条打印 `[PASS]/[FAIL]/[WARN]/[SKIP]` + 一行证据，
**有 FAIL 就阻断发布**，只有 WARN 时看警告后自行决定。

退出码即结论：`0` 全通过可发布 · `1` 有 FAIL 阻断发布 · `2` 仅 WARN 可发布但需看警告。

## 1. 事实源在哪（动手前先读，不要凭记忆）

| 要知道什么 | 去读哪 |
|---|---|
| 检查项真值（哪些路径必须被忽略） | `.gitignore`（唯一真值处） |
| 仓库边界与「代码 vs 个人资料」分区 | `SPEC.md` §1「**仓库边界**」 |
| 接口清单（口径漂移的对照物） | `SPEC.md` §3 接口表 ↔ `server/src/routes/*.js` |
| 本地资料目录定义（不得入库的那些） | `SPEC.md` §1 结构树 + `RUN.md` 的 `DATA_DIR` 说明 |
| 环境变量样例与必填项 | 根 / `server/` / `asr/` 三份 `.env.example` |
| 自测脚本有哪些、各自跑什么 | `server/scripts/*.mjs`；套路见 `skills/backend-verify/SKILL.md` |
| 线上地址与部署形态（公网健康检查） | `RUN.md` |
| 每条检查**为什么存在** | `AGENTS.md` 对应 Day 条目 |

## 2. 四类检查（为什么是这四类）

| 类 | 查什么 | 为什么是红线 |
|---|---|---|
| ① 密钥与凭据 | 已跟踪文件里有无真密钥特征；`.env` 是否被忽略且未入库；三份 `.env.example` 是否齐全；**compose 里有无被注释掉的 env 行** | 一旦推上公开仓即**不可撤回**（历史仍在），只能轮换密钥；被注释掉的 env 则是「本地能跑、上线不认」的经典坑 |
| ② 隐私边界 | `data/ memory drafts .workbuddy .pi` 是否被忽略；`data/` 根锚定是否误伤 `web/src/data/` | 公开仓只放代码与文档，个人资料进私有仓 |
| ③ 构建与自测 | 后端 `node --check`、前端 `npm run build`、各套验证脚本、链接链路自测 | 「我这能跑」≠「发出去能跑」，必须可复现 |
| ④ 发布形态一致性 | 公网 `/api/health`、SPEC 接口数 vs 代码路由数、工作区是否干净、本地是否已推送 | 文档与代码漂移、带未提交改动发布，都是线上事故的常见起因 |

**四类的顺序是有意的**：①② 是「能不能发」，③④ 是「发出去对不对」。① 里任一 FAIL 就**不必往下看**。

### 2.1 专项：被注释掉的 env（部署「本地能跑、上线就炸」）

**事故长相**：Dockerfile 里写 `# ENV DATA_DIR=/app/data`、compose 里写
`#   DATABASE_URL: postgres://…`——作者以为「写在文件里 = 已配置」，
实际镜像/容器里**根本没有这个变量**，进程静默走代码默认值。
症状是「本地跑得好好的，上线就 503 / 连错库 / 找不到目录」，而报错现场离病根很远。

**为什么容易踩**：
- `# ENV X=1` 和 `ENV X=1` **语义完全相反**（前者等于没写），但视觉上只差一个字符；
- compose 的注释里本来就大量出现变量名（说明性文字），**不能一律报错**；
- `.env.example` 的注释则是**刻意**的（样例不该带默认值），所以**只查 compose / Dockerfile，不查 `.env.example`**。

**判据（收窄到只打真歧义）**：整行是注释，**且去掉注释符后的首个 token 就是一条赋值**：

```bash
grep -nE '^[[:space:]]*#[[:space:]]*[A-Za-z_][A-Za-z0-9_]*[[:space:]]*[:=]' docker-compose.yml
```

| 写法 | 命中 | 为什么 |
|---|---|---|
| `# CHROMA_URL: http://chroma:8000` | ✅ FAIL | 去掉 `#` 就是一条真赋值，显然是「被注释掉了」 |
| `# 不要删除下面的 DATA_DIR` | ❌ 不命中 | 注释符后首 token 是 `不要`，是说明性文字 |
| `# 命名卷：临时媒体…` | ❌ 不命中 | 同行内出现 `DATA_DIR` 但不以赋值开头 |
| `.env.example` 的 `# KEY=` | ❌ 不查 | 样例**应当**留空，属预期写法 |

**修法**：要么恢复成真赋值，要么把注释改成说明性句子（别让它长得像赋值）。
**误伤边界**：`$schema:`、中文冒号等非 `[A-Za-z_][A-Za-z0-9_]*` 起头的注释不会命中。

## 3. 怎么跑

```bash
bash skills/release-check/scripts/release-check.sh
```

- **只读**：脚本不写任何文件、不改 `.gitignore`、不 commit、不 push。
- **幂等**：连跑两次结果一致（③ 的前端构建会产出 `web/dist/`，那是构建产物，已被忽略）。
- **可在任意 CWD 调用**：脚本自己 `cd` 到仓库根。
- 结果落证：把输出原样贴进 `runs/YYYY-MM-DD-dayNN.md`，不要转述。

## 4. 判定与处置

| 结果 | 含义 | 处置 |
|---|---|---|
| `[FAIL]` | 触碰红线 | **阻断发布**。修掉再跑，不要「先发了再说」 |
| `[WARN]` | 值得看一眼但不拦 | 逐条确认：能解释就写进留证，不能解释就当 FAIL 处理 |
| `[SKIP]` | 前置条件不满足（如没装 `node_modules`） | 记下，**不要当 PASS**；发布环境必须把 SKIP 消掉 |
| `[PASS]` | 通过 | — |

**发布前 SKIP 应尽量为 0**：SKIP 意味着「这条我根本没验」。

## 5. 踩坑清单（写/改检查脚本时必看，都是实测踩过的）

| 坑 | 现象 | 解法 |
|---|---|---|
| **grep 文本判成败必误报** | 检查「验证脚本过没过」时 `grep "FAIL"`，结果命中了日志里的业务码 `VALIDATION_FAILED`（含 "FAIL" 子串），把本该 PASS 的判成 FAIL | **一律用退出码判定**：`OUT=$(...); RC=$?; [ "$RC" -ne 0 ] && fail ...`。文本搜索只能用来**提取摘要行**，不能用来判成败 |
| **接口数正则漏前缀** | SPEC 接口表分三组：纯数字（业务）+ `S` 前缀（管理）+ `M` 前缀（运维），正则只写 `^\| [A-Z][0-9]+` 会只匹配到一部分，误报「口径漂移」 | 正则要同时覆盖三种：`^\| [A-Za-z]*[0-9]+ \| \`(GET\|POST\|PATCH\|DELETE\|PUT)`，并与代码侧逐项对齐后再定稿 |
| **`git check-ignore` 对不存在的路径也返回非 0** | 目录不存在时被误判为「未被忽略」→ 假 FAIL | 先 `[ -e "$p" ]` 区分「不存在（规则在位即可）」与「存在但未忽略（真 FAIL）」 |
| **`data/` 必须根锚定** | 裸写 `data/` 会连 `web/src/data/` 一起忽略，前端源码消失 | 用 `/data/` 根锚定；检查脚本里要**专门验证这一步没误伤**（`git check-ignore -q web/src/data` 应为非 0） |
| **文件名含 `secret`/`token` 会被自己的规则吃掉** | 留证文件 `*secrets*.txt` 静默不入库（`.gitignore` 第 7 行 `*secret*`），`git status` 里看不到 | 留证命名避开这些词（如 `shot1-keyscan.txt`）；**新建留证后必须 `git status` 确认它在列** |
| **注释掉的 env 别一律报错** | 把「注释行里出现变量名」都判 FAIL，会命中大量说明性注释（`# 不要删除 DATA_DIR`、`# 命名卷…`）→ 误报满天飞 | 判据收窄为「去掉注释符后**首个 token 就是赋值**」（见 §2.1 正则）；`.env.example` 的注释是预期写法，**不查** |
| **`[ -z "$HITS" ]` 与 `set -e`** | 管道前段失败会让脚本提前退出，后续检查整段不跑 | 脚本头用 `set -uo pipefail`（**不**加 `-e`），并用 `|| true` 兜住预期内的非零退出 |

## 6. 新增一条检查的规格

1. **先找真值处**：能写进 §1 表格的才是「有事实源」的检查；凭记忆写死的阈值迟早漂移。
2. **一句话说清 FAIL 判据**：什么情况必须阻断发布？说不清就降级成 WARN。
3. **证据可复现**：FAIL 那行要打印出**具体命中了什么**（文件/行/条数），读的人能自己去复核。
4. **别自作聪明改文件**：检查脚本只读。要修就单独提一句，让人来决定。

## 7. 留证格式

产物写 `runs/YYYY-MM-DD-dayNN.md`，至少含：
- 环境一句（本机 / 发布机；HEAD commit；日期时区）
- **原始输出**（脚本打印的 `[PASS]/[FAIL]/[WARN]/[SKIP]` 与末尾计数行）——不转述、不改写
- 每条 WARN/SKIP 的**人工结论**（能解释 / 已转 FAIL）
- 「故意留个问题能否查出」的验证记录（见 §8）
- 未做清单（如实登记）

## 8. 自检：这个检查 Skill 会不会虚报通过？

「跑出全绿」本身不能证明检查有效——**必须故意弄坏一项，看它能不能查出来**。流程：

1. 挑一条有明确 FAIL 判据的检查（①② 类最直观）；
2. **制造**该问题（例如：让 `.env` 落入版本控制、或写一行形如真密钥的占位串）；
3. 重跑，**确认它真的报 FAIL 且阻断**（退出码 `1`，末尾打印「阻断发布」）；
4. **还原**问题，重跑确认回到 FAIL=0；
5. 截图 / 贴原文存证，并记下「弄坏的是哪一项、靠哪条判据查出来的」。

> 只做到第 3 步就发出去是危险的一半：**没有第 4 步的还原，你会把问题一起发上去**。

- [ ] 连跑两次结果一致；SKIP 已在留证里逐条解释
- [ ] 没碰真实 `data/`、没碰数据库、没 push
