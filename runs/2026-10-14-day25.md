## 2. ① 规划检查项（为什么是这 4 类）

| 类 | 检查项 | 为什么是红线 / 依据 |
|---|---|---|
| **① 密钥与凭据**（5 项） | 无硬编码密钥特征；`.env` 被忽略；`.env` 未入库；三份 `.env.example` 齐全；**compose 无注释掉的 env** | 推上公开仓即**不可撤回**（历史仍在），只能轮换密钥；被注释掉的 env 是「本地能跑、上线就炸」的经典坑（§3.2） |
| **② 隐私边界**（6 项） | `data/ memory drafts .workbuddy .pi` 被忽略；`data/` 根锚定未误伤 `web/src/data/` | 公开仓只放代码文档，个人资料进私有仓（`SPEC.md` §1 仓库边界） |
| **③ 构建与自测**（6 项） | 后端 58 个 js 语法；前端构建；`day22/23/24-verify`；链路自测 | 「我这能跑」≠「发出去能跑」，必须可复现 |
| **④ 发布形态一致性**（4 项，含 1 WARN） | 公网 `/api/health`；SPEC 接口数 vs 代码路由数；工作区干净；本地已推送 | 文档与代码漂移、带未提交改动发布，是线上事故常见起因 |

**顺序是有意的**：①② = 「能不能发」，③④ = 「发出去对不对」。① 里任一 FAIL 就不必往下看。
全部检查项的真值都**指向项目事实源**（`.gitignore` / `SPEC.md` / `RUN.md` / `server/scripts/*.mjs`），
脚本里不硬编码清单——否则两处写值必然漂移（这条原则沿用 `frontend-rules` / `backend-verify`）。

## 3. 今日要掌握的问题：故意弄坏哪一项？

**答：把 `.gitignore` 里的 `.env` / `.env.*` 两条规则注释掉。**

选的为什么是这一项：一是 ①② 类**判据最明确**（`git check-ignore` 只有是/否，没有中间态）；
二是它对应**最不可撤回的事故**——密钥文件一旦进入公开仓历史，删掉当前版本也没用。

### 三次实跑对照（这就是「它没有虚报通过」的证据）

| 阶段 | 结果计数 | `.env 已被忽略` | 退出码 | 末尾结论 |
|---|---|---|---|---|
| 植入前（基线） | 19 通过 / 0 失败 / 1 警告 | PASS | `2` | 无 FAIL，可发布但建议先看警告 |
| **植入后（缺陷态）** | **18 通过 / 1 失败 / 1 警告** | **FAIL** | **`1`** | **有 FAIL，阻断发布** |
| 还原后 | 19 通过 / 0 失败 / 1 警告 | PASS | `2` | 无 FAIL，可发布但建议先看警告 |

### 三个「不虚报」的证据

1. **定点命中，不连带误报**：缺陷态下只有 ①「`.env` 已被忽略」一条翻红，
   其余 **18 项仍是 PASS**，②③④ 三节全绿 → 不是一片飘红式的假报警。
2. **真的拦得住**：末尾文案从「可发布」翻为「**阻断发布**」，退出码 `2 → 1`
   → 放进 CI 会 fail job，而不只是印一行提示。
3. **证据可复核**：FAIL 行打印出 `.gitignore 未覆盖 .env`
   → 读的人可自行 `git check-ignore -v .env` 复核，无需相信结论。

### 还原留证（这一步不能省）

```bash
cp .gitignore .gitignore.bak-day25verify      # 植入前先备份
# ...植入缺陷 → 跑检查 → 截图...
```

→ 实验对仓库**零残留**。

### 3.2 第二轮：追加「compose 无注释掉的 env」检查项（22:17）

**动因**：使用者要求补一项针对「docker 部署时注释掉 env 影响环境变量」的检查。

**为什么值得单列一条**：`# ENV X=1` 与 `ENV X=1` **语义完全相反**（前者等于没写），视觉上只差一个 `#`。
典型写法是 `#   DATABASE_URL: postgres://…` 留在 compose 里，作者以为「写进文件就配好了」，
实际容器里没有该变量 → 进程静默走代码默认值 → 表现为「本地跑得好好的，上线就 503 / 连错库」，
且**报错现场离病根很远**。

**判据设计（关键在「别一律报错」）**：compose 的注释里本来就大量出现变量名（说明性文字），
一律拦会误报满天飞。故收窄为「整行是注释，**且去掉注释符后的首个 token 就是一条赋值**」：

```bash
grep -nE '^[[:space:]]*#[[:space:]]*[A-Za-z_][A-Za-z0-9_]*[[:space:]]*[:=]' docker-compose.yml
```

| 写法 | 命中 | 理由 |
|---|---|---|
| `# CHROMA_URL: http://chroma:8000` | ✅ FAIL | 去掉 `#` 就是真赋值，显然「被注释掉了」 |
| `# 不要删除下面的 DATA_DIR` | ❌ | 注释符后首 token 是 `不要`，属说明文字 |
| `# 命名卷：临时媒体…` | ❌ | 同行出现 `DATA_DIR`/变量名，但不以赋值开头 |
| `# 官方镜像默认监听 8000（EXPOSE 8000/tcp）` | ❌ | 同上 |
| `.env.example` 里的 `# KEY=` | ❌ 不查 | 样例**应当**留空，属预期写法 |

**误伤自证**：在本项目真实 `docker-compose.yml` 上跑，命中 **0 行**（该文件有 7 处含变量名的注释，全部正确放行）。

**验证——故意植入 2 行**（把 `CHROMA_URL` / `DATABASE_URL` 注释成配置）：

| 阶段 | 结果计数 | `compose 无注释掉的 env` | 退出码 |
|---|---|---|---|
| 植入前 | 20/0/1 | PASS | `2` |
| **植入后** | **19/1/1** | **FAIL — `命中 2 行：82: # CHROMA_URL: … 87: # DATABASE_URL: …`** | **`1`** |
| 还原后 | 20/0/1 | PASS | `2` |

FAIL 行直接给出**行号 + 原文**，可 `sed -n '82p;87p' docker-compose.yml` 自行复核。
**还原**：`cp` 备份 → 植入 → 跑 → `diff` 无差异 → `rm`；`git diff --stat docker-compose.yml` 为空 → 零残留。

**同步留档**：`SKILL.md` 新增 §2.1 专项小节（判据表 + 误伤边界）与踩坑清单一行（「注释掉的 env 别一律报错」）。

## 4. ② 制作检查 Skill 时修掉的自家缺陷

写这个 Skill 的过程本身踩了两个坑，都已写进 `SKILL.md` §5 踩坑清单（避免下次重犯）：

| 坑 | 现象 | 修法 |
|---|---|---|
| **grep 文本判成败** | 检查「验证脚本过没过」时 `grep "FAIL"`，命中了日志里的业务码 `VALIDATION_FAILED`（含 "FAIL" 子串），把本该 PASS 的 day22/day23 判成 FAIL | **改用退出码判定**：`OUT=$(...); RC=$?; [ "$RC" -ne 0 ] && fail`。文本搜索只用来提取摘要行，不判成败 |
| **接口数正则漏前缀** | 只写 `^\| [A-Z][0-9]+` 时 SPEC 侧只匹配到 14 条，代码侧 38 条 → 误报「口径漂移」 | 正则补全三种前缀：纯数字（业务）+ `S`（管理）+ `M`（运维）→ 两侧均 38，与代码一致 |

另外一条经验：**留证文件名不能含 `secret` / `token`**——`.gitignore` 的 `*secret*` 会把它吃掉，
`git status` 里根本看不到（前日已栽过一次，本次命名一律避开）。
