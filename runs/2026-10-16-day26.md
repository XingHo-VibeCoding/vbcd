## 3. 板块③ 静态托管回退演练

### 3.1 第一次尝试：手册主路径 —— **失败**

```bash
WEB_IMAGE=vbcd-web:prev-cc6aa14 docker compose up -d --no-deps --force-recreate web
# → Container vbcd-web-1  Recreated / Started      （耗时 2s）
# → 但运行镜像仍是 c5bc0df43458，index.html 仍是 index-AshHe_0w.js
```

排查：

```bash
$ WEB_IMAGE=vbcd-web:prev-cc6aa14 docker compose config | grep -A3 '^  web:'
  web:
    build:
      context: /home/bird/vbcd/web      ← 只有 build，没有 image
```

**根因**：`docker-compose.yml` 的 `web` 服务只写了 `build: ./web`，**没有 `image:`**。
compose 对「只有 build」的服务，`up` 时会**优先按 build 重建**，`WEB_IMAGE` 这个环境变量**根本没有任何地方引用它**——
它是我凭想象写进手册的，**从来没生效过**。

### 3.2 第二次尝试：加 `--no-build` —— 仍然失败

```bash
WEB_IMAGE=... docker compose up -d --no-deps --force-recreate --no-build web
# → 容器照样 Recreated，镜像照样 c5bc0df43458
```

`--no-build` 只是「不许我构建」，compose 仍会把它解析成「该服务的镜像由 build 决定」，于是拿本地已有的 `vbcd-web:latest` 起容器。

### 3.3 第三次尝试：兜底方案 —— **成功**

```bash
docker rm -f vbcd-web-1
docker run -d --name vbcd-web-1 --restart unless-stopped \
  --network vbcd_internal -p 80:80 vbcd-web:prev-cc6aa14
```

| 验证项 | 结果 |
|---|---|
| 运行镜像 | `ed79066f8b68` ✅ |
| `index.html` 引用（源站） | `/assets/index-COMn3COT.js` ✅（旧版） |
| `HTTP /` | `200` |
| 旧版 js 可访问 | `200` |
| `/api/health` 反代 | `200`（后端未被牵连） |
| 公网 CDN 引用 | `/assets/index-COMn3COT.js`，`cf-cache-status: DYNAMIC` ✅ |
| 源站直连引用 | `/assets/index-COMn3COT.js` ✅ |

**两版可区分的硬证据**（不是靠肉眼）：

| 字符串 | 旧版 `cc6aa14` | v1.0 `1387c1c` |
|---|---|---|
| `Planner` | 0 | 1 |
| `Journal` | 0 | 1 |
| `About` | 0 | 1 |
| `主页` | 5 | 4 |
| `档案` | 17 | 16 |

> v1.0 把导航改成英文（Home/Archive/Planner/Journal/Agent/About），所以 `Planner/Journal/About`
> 在旧版里**是 0**。这条判据比「看一眼页面」可靠：**数字不会说谎，也不会被缓存骗。**

## 5. 恢复记录（实测）

**命令**：与回滚同一条路径，只换 tag —— 也就是**回滚和恢复用的是同一套动作**，没有「回滚有专门流程、恢复靠手忙脚乱」这种不对称。

| 时刻 | 动作 | 结果 |
|---|---|---|
| T+0 s | `docker rm -f vbcd-web-1` | 旧容器（`ed79066f8b68`）停止并移除 |
| T+1 s | `docker run -d ... vbcd-web:v1.0` | 新容器启动，镜像 `c5bc0df43458` |
| T+2 s | 源站核对 `index.html` | `/assets/index-AshHe_0w.js` |
| T+2 s | 源站 bundle md5 | `d57b8707356d0af7b5e77cd6f2a52bfd` |
| T+3 s | 公网 + `/api/health` | 页面 200、引用一致、`ok:true` |
| **合计** | **命令发出 → 公网确认** | **约 3 s** |

### 5.1 恢复后额外做的三件事（来自 ROLLBACK.md §5）

1. **对外口径**：`CHANGELOG.md` / `README.md` 的 v1.0 状态未改动——因为恢复的就是 v1.0，公告无需变更；回滚演练本身只在 `runs/` 留证。
2. **镜像可追溯**：`vbcd-web:v1.0` 与 `vbcd-web:prev-cc6aa14` **两个镜像同时保留**，任何一个都能在 3 秒内切上去，也都能再切回来。
3. **数据未受影响**：全程只替换了 `web` 容器（`--no-deps` / `docker run` 都不碰 `pg`、`chroma`、`data/`），`/api/health` 里后端依赖项正常 → 证实「静态回退不会连带数据风险」。

### 5.2 一句话结论（今日要掌握的问题）

> **回滚演练花了多久？** 成功路径 **3 秒**；含两次踩坑排查约 **2 分钟**。
> **真出事敢不敢用？** 敢——但只敢用 `docker rm` + `docker run` 这条路径。`docker compose up` 那条路**实测无效且会谎报成功**，这是今天最值钱的一条负知识。
